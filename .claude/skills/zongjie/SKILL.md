# 改动总结

只在本地读改动，**不做任何写操作**：不 `git add`、不 `git commit`、不 `git push`、不改文件。
用户自己会复制总结去提交/上传。

## 1. 先看有哪些改动

```
git status --short
git diff HEAD --stat
```

`git diff HEAD` 同时覆盖「已暂存」和「未暂存」，正好对应编辑器的 CHANGES 面板。

- 两条都为空 → 直接回复：「改动区是干净的，当前没有未提交的改动。」然后结束，不要编造内容。
- `--stat` 为空但有 `??` 文件 → 本次全是新增文件，转去第 2 步读它们。

## 2. 再看具体改了啥

按文件分批看 diff，别一次性把整个 diff 灌进来（大 diff 会淹掉重点）：

```
git diff HEAD -- "<路径>"
```

- `??` 未跟踪的新文件用 Read 工具读；文件很长就只读开头和结构，别整篇读。
- 只挑「有意义的改动」写：逻辑、界面、文案、配置、接口。
- 跳过噪音：`.log`、`dist/`、`node_modules/`、`AI日报_*.md`、纯格式化/缩进/依赖锁文件、以及纯粹的时间戳或生成数据变动。这些如果在 status 里出现，只在末尾一句带过。

## 3. 组织总结

这个仓库的提交信息风格是**口语化中文、一句话说清做了什么**，比如：

- 修复开关功能，点「推送中」现在会变成「已暂停」
- 企业微信 ETF 简报改为单条发完，不再截断 A 股候选

照这个风格写，不要 conventional commit 前缀（`feat:` / `fix:` 之类），不要 emoji，不要「本次提交」这种废话开头。用户视角优先：先说用户能感知到的变化，再说技术实现。

## 4. 输出格式

严格用下面这个模板，整段包在代码块里方便一键复制：

````
<一句话总结>

改动明细：
- <文件或模块>：<做了什么>
- <文件或模块>：<做了什么>

涉及 N 个文件（新增 X / 修改 Y / 删除 Z）
````

要求：

- 一句话总结 ≤ 40 字，能直接当提交信息用。
- 改动明细 2～5 条，按重要性排序，每条一行，说人话，不复制代码。
- 代码块外不要重复贴一遍总结内容；代码块外可以补一句提醒（比如「有个改动看起来不完整」）。
- 如果发现明显的问题（漏改的引用、调试代码没删、写死的临时值），在代码块外单独点出来，用户认可后再问要不要改。
